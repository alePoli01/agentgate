## Context-Aware Tier System & Initialization
1. Core framework files (skills, agents, instructions) are strictly maintained in `.ai/`.
2. **Path Convention Clarity:**
   - `.ai/` = framework infrastructure (state files, lifecycle, rules, skills).
   - `project-data/` = user-generated project outputs (source code, assets, data).
   All project-specific outputs generated by you MUST be saved in `project-data/` or a similarly designated output folder. Never mix the two.

**CRITICAL INITIALIZATION STEP**: The very first action you must take in any session is to check for the existence of `.ai/MODEL_ENV.md`.
1. If `.ai/MODEL_ENV.md` exists, read it to determine your Model Tier.
2. If `.ai/MODEL_ENV.md` does NOT exist, you must **IMMEDIATELY STOP** and ask the user: *"What AI model are you currently using to run this project? (e.g. Gemini 3.1 Pro, Llama 3, Claude 3.5 Sonnet)"*.
3. Once the user answers, categorize the model (e.g. Gemini/GPT-4/Claude = Large; smaller models = Small/Medium) and write the tier to `.ai/MODEL_ENV.md`.

## Override Hierarchy
The framework's rules are structured in a strict hierarchy. Lower items override higher items:
1. `core-rules.md` (Universal defaults, priority 0)
2. **Tier Thresholds** (The Tier specified in `MODEL_ENV.md` overrides global limits, dictating `MAX_ITERATIONS` and context gates).

> **Note**: In the dev-repo (where the framework itself is being developed), `.ai/` corresponds to the `llm-framework/` directory.

## MCP Tool Detection (Onboarding Step)

During initial workspace setup, immediately after reading `core-rules.md` and determining the Model Tier, you MUST detect which MCP tools are available in the user's environment.
Save results to `.ai/MODEL_ENV.md` under a `## MCP Tools` section using this exact schema:

```yaml
mcp_tools:
  browser: false        # true if chrome-devtools-mcp or equivalent is available
  filesystem: true      # true if a filesystem MCP is available
  git: false            # true if a git MCP is available
```

**Detection method:** Attempt to call a known tool from each MCP server. If the call succeeds or the tool is listed as available, mark as `true`. If it errors or is unavailable, mark as `false`.

**Why this matters:** The `test.md` skill uses this registry to decide between automated browser verification (MCP path) and CLI fallbacks or human checkpoints (non-MCP path). A missing entry is treated as `false`.

## Subagent Check (Onboarding Step)

After reading `core-rules.md` and detecting MCP tools, check whether you have been
spawned as a subagent by inspecting the context you were given.

**Signal that you are a subagent**: Your briefing contains the line:
`[AGENTGATE] BRIEFING BLOCK — Paste this into a new chat`

If this signal is present:
1. Do NOT run the standard user-facing onboarding flow.
2. Read `.ai/SUBAGENT_STATE.md` immediately (OBSERVE verb).
3. Identify your assigned task from the ## Your Task section of the briefing.
4. Execute your role-specific instructions WITHOUT asking for clarification.
   (All ambiguity was resolved before you were spawned.)
5. When done, write your TELL row to the whiteboard and output your result.

**If the signal is NOT present**: You are the primary agent in a standard session.
Continue with normal onboarding (read core-rules.md, check MODEL_ENV.md, etc.).
